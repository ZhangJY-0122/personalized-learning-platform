# 成员 3：个性化学习推荐系统与算法详细方案

版本：V1.1（实施优化版）  
对应题目：F21  
项目名称：基于知识追踪与混合推荐算法的个性化学习推荐系统  
开发目标：第一周完成独立系统，第二周接入 F13 综合平台

说明：V1.1 只优化成员 3 的实施顺序、可靠性要求和风险控制；《02-统一数据与接口契约》仍以团队冻结的 V1.0 为准，公共 API 或事件变更须经三名成员共同确认。

## 1. 项目定位

本项目负责将学生的学习行为转换为可解释的知识掌握状态，并据此识别薄弱知识点、推荐资源和习题、生成个性化学习路径。

实施时优先保证以下主链路真实闭环，不以算法数量代替系统完整性：

```text
学习事件
  → 幂等消费和标准化交互
  → 学生画像及知识掌握度
  → 薄弱知识点
  → 可解释资源/习题推荐
  → 个性化学习路径
  → 完成推荐内容
  → 掌握度、推荐和路径动态更新
```

项目必须满足两种运行模式：

### 1.1 独立模式

- 使用自己的简化登录和初始化数据。
- 可以导入课程、知识点、资源、题目和学习行为。
- 能单独展示画像、掌握度、推荐、路径和实验结果。
- 不依赖成员 1、2 的系统即可验收。

### 1.2 综合模式

- 使用成员 1 签发的统一 JWT。
- 使用成员 1 的用户、课程、知识点、资源和题目 UUID。
- 消费教学考试服务产生的学习事件。
- 向统一前端和 BFF 提供掌握度、薄弱点、推荐和路径接口。

## 3. 系统架构

```text
                  Vue 3 个人前端
                         │
               Spring Boot 业务服务 :8083
          权限、数据导入、业务编排、结果保存
             │                        │
      recommender_db          FastAPI 算法服务 :8001
                                      │
                         BKT / DKT / 推荐 / 路径
                                      │
                         预训练模型和实验结果文件
```

职责规定：

- Vue 只调用 Spring Boot，不直接访问 FastAPI。
- Spring Boot 负责鉴权、数据库、事件幂等、任务编排和结果持久化。
- FastAPI 尽量无状态，加载指定模型并返回预测结果。
- 离线训练脚本不进入在线请求链路。
- 在线接口不得现场训练模型。
- FastAPI 不可用时，Spring Boot 使用已保存掌握度、BKT 或规则基线降级。
- Spring Boot 是业务事实来源，负责模型路由、目录版本校验、事务、推荐/路径失效和对外错误处理。
- FastAPI 不判断事件是否重复，不直接对外暴露，不单独维护业务主数据。
- FastAPI 调用超时建议为 1～2 秒；超时后立即执行降级，不阻塞整个业务链路。
- 离线训练产物必须经过 `model_registry` 注册后才能被在线服务加载。

### 6.4 数据隔离规则

## 7. 知识追踪算法

### 7.1 规则统计基线

根据某学生在某知识点最近 N 次作答的加权正确率估计掌握度。该方法用于：

- 最简单对照实验
- BKT、DKT 均不可用时的最终降级
- 检查模型输出是否明显异常

### 7.2 BKT

每个知识点维护：

```text
P(L0) 初始掌握概率
P(T)  学习转移概率
P(G)  猜测概率
P(S)  失误概率
```

每次收到 `QUESTION_ANSWERED` 后更新对应知识点的掌握概率。多知识点题目按 `knowledgeItems.weight` 更新。

BKT 优点：

- 可解释
- 小数据可用
- 支持新课程冷启动
- 可以增量更新

BKT 是在线稳定基线。即使 DKT 已完成，也必须保留 BKT 参数、更新过程和结果，以支持冷启动、目录版本不匹配和算法服务异常时降级。

### 7.3 DKT

使用 LSTM 输入按时间排列的“知识点 + 作答结果”序列，预测下一次对各知识点作答正确的概率。

参考：[Deep Knowledge Tracing 原论文](https://proceedings.neurips.cc/paper_files/paper/2015/hash/bac9162b47c56fc8a4d2a519803d51b3-Abstract.html)

训练要求：

- 按学生和时间顺序构建序列。
- 不打乱同一学生的历史顺序。
- 对过长序列进行固定窗口切分。
- 记录知识点映射表。
- 保存模型、参数、课程 ID、目录版本、数据版本和随机种子。

多知识点题目的 V1.1 处理规则：

- BKT 按 `knowledgeItems.weight` 更新全部关联知识点。
- DKT 以权重最高的知识点作为本次交互的主知识点；权重相同时按稳定的知识点 ID 顺序选择。
- 薄弱点和推荐继续使用全部关联知识点及权重。
- 该规则必须写入预处理脚本、在线推理代码和算法文档，避免训练与在线行为不一致。

### 7.4 实验设计

必做对比：

1. 最近 N 次正确率
2. BKT
3. DKT

可选扩展：SAKT。只有前三项、推荐系统和个人项目完整完成后再加入。

数据切分：

- 按每名学生的时间顺序使用 70% 训练、10% 验证、20% 测试。
- 固定 3 个随机种子。
- 报告平均值和标准差。

指标：

- AUC
- Accuracy
- RMSE
- LogLoss

DKT 不一定必须优于 BKT。如果结果不理想，应分析数据量、序列长度、知识点稀疏度和参数，而不是修改或虚构指标。

## 8. 新课程和新用户冷启动

公开数据集中的技能编号不能直接迁移到 Java、数据结构或计算机网络。

模型路由规则：

```text
无学习行为
  → 入门测评 + 课程难度 + 热门内容

课程行为较少或无匹配模型
  → BKT

存在匹配 courseId 与 catalogVersion 的活动模型
  → DKT

DKT/FastAPI 异常
  → BKT

BKT 数据也不足
  → 最近正确率或默认掌握度
```

三门演示课程可以使用明确标注为合成的课程内数据训练 DKT。公开数据集实验结果和演示课程结果必须分开呈现。

模型加载前必须同时校验：

```text
model.course_id == request.course_id
model.catalog_version == current.catalog_version
model.status == ACTIVE
model.checksum 与实际产物一致
知识点映射和特征结构版本兼容
```

任一条件不满足时不得继续使用该 DKT 模型。

## 9. 薄弱知识点识别

基础规则：

- 掌握度低于 0.6 判定为薄弱。
- 按掌握度升序排列。
- 同时考虑知识点重要度、最近错误次数和先修影响范围。
- 行为少于最低阈值时标记为“证据不足”，不直接断言学生薄弱。

薄弱点接口应同时返回 `mastery`、`evidenceCount`、`confidence`、`recentErrorRate`、`lastActivityAt` 和得分组成，便于前端解释和验收追溯。

建议薄弱得分：

```text
weakness =
0.60 × (1 - mastery)
+ 0.20 × recentErrorRate
+ 0.10 × importance
+ 0.10 × prerequisiteImpact
```

## 10. 混合推荐

### 10.1 候选生成

1. 选择掌握度最低的 3～5 个知识点。
2. 检查未掌握的先修知识点。
3. 查询关联资源和习题。
4. 排除已经完成且无复习需要的项目。
5. 控制资源类型和难度多样性。
6. 无候选时返回明确原因。

### 10.2 排序得分

P0 基线策略使用四项可验证得分：

```text
总得分 =
0.45 × 薄弱知识匹配
+ 0.25 × 预测难度匹配
+ 0.20 × 内容相似度
+ 0.10 × 学习偏好匹配
```

习题预测正确率接近 0.65 时，难度匹配得分最高。

P1 扩展策略可以加入协同过滤。用户有效行为少于 10 条、交互用户过少或矩阵过于稀疏时：

- 禁用协同过滤，不填充虚拟得分。
- 将相应权重转移给薄弱知识匹配和内容相似度。
- 对所有有效权重重新归一化。

新颖度和多样性优先作为排序后处理：

1. 先按相关性得分取前 20 个候选。
2. 再限制相同知识点、资源类型和难度区间的数量。
3. 最终返回前 5～10 个结果。

如保留原七项策略用于对比实验，必须在 `score_detail_json` 中保存每项真实子分数、启用状态和归一化权重。

### 10.3 推荐解释

每条结果至少生成两条可验证解释，例如：

```text
该知识点当前掌握度为 0.42。
最近三次相关题目中有两次答错。
该资源难度与当前能力匹配。
目标知识点的先修内容已经基本掌握。
```

解释由规则和真实计算结果生成，不调用大模型编造。

`reason_json` 应同时保存解释文本和可追溯依据：

```json
{
  "reasons": [
    {
      "type": "LOW_MASTERY",
      "knowledgeId": "uuid",
      "value": 0.42,
      "text": "该知识点当前掌握度为 0.42"
    },
    {
      "type": "RECENT_ERRORS",
```

## 11. 学习路径规划

知识点先修关系必须为有向无环图。

生成步骤：

1. 找出掌握度低于 0.6 的目标知识点。
2. 向前追溯未掌握的先修知识点。
3. 对目标子图执行拓扑排序。
4. 每个知识点安排“学习资源—基础题—进阶题—复测”。
5. 完成复测后更新掌握度。
6. 根据新掌握度重新规划剩余路径。

路径分为两层：

- 知识层：按照先修关系排列目标知识点。
- 内容层：为每个知识点安排资源、基础题、进阶题和复测。

动态重规划时不得覆盖或删除旧路径。旧路径标记为 `INVALIDATED` 并记录原因，新建递增的 `path_version`，保留前后路径供追溯和答辩展示。

如果检测到环、缺少内容或目录版本不匹配，停止自动规划并返回具体原因。

研究亮点应表述为“知识追踪结果如何改变路径和触发动态重规划”，不能将普通拓扑排序描述为深度学习。

## 13. 事件消费

接收：

```text
COURSE_ENROLLED
RESOURCE_VIEWED
RESOURCE_COMPLETED
QUESTION_ANSWERED
EXAM_SUBMITTED
```

产生：

```text
RECOMMENDATION_EXPOSED
RECOMMENDATION_CLICKED
RECOMMENDATION_COMPLETED
```

V1.1 默认由 `POST /recommendations/{recommendationId}/feedback` 接收并保存推荐曝光、点击、完成及主观反馈，前端不得对同一行为同时提交反馈接口和学习事件。

成员 3 是否需要把推荐行为回传成员 1、由谁生成 `eventSeq`，当前统一契约尚未明确。该项列为团队待冻结事项；冻结前先在成员 3 内部持久化，不自行扩展成员 1 的事件生产接口。后续如确认回传，应采用本地 outbox 和明确的接收 API，避免双写与重复事件。

消费规则：

1. 按批内 `eventSeq` 升序读取，但只使用 `eventId` 作为业务幂等键。
2. 使用 `eventId + sourceService` 检查是否已处理；重复事件返回成功，不重复更新。
3. 检查用户、课程、题目和知识点快照。
4. 写入标准学习交互并更新画像特征。
5. 调用匹配的知识追踪模型；模型不匹配或调用失败时按路由规则降级。
6. 更新掌握度、掌握度历史和最后处理序号。
7. 必要时令旧推荐和旧路径失效，并记录失效原因。
8. 写入消费成功日志。

一致性要求：

- 同一 `userId + courseId` 的掌握度更新必须串行化或使用乐观锁，避免并发覆盖。
- 学习交互、当前掌握度、掌握度历史和消费日志尽量在同一数据库事务中提交。
- 不得先写 `SUCCEEDED` 再更新掌握度。
- 批量接口允许部分成功，失败列表必须包含 `eventId`、错误码和可重试标记。
- 晚到事件第一版记录告警并进入人工检查，不自动执行全量历史重放。

缺少目录快照时保存为 `PENDING_COMPENSATION`，记录 `next_retry_at`，待快照补齐后重新处理，不直接丢弃事件。

目录版本变化时：

- 停止使用不匹配目录版本的模型。
- 将旧推荐批次和活动路径标记为 `INVALIDATED`。
- 已删除知识点的掌握度保留历史，但不作为当前有效结果展示。
- 新知识点使用默认掌握度或 BKT 冷启动。
- 重新同步资源、题目及其知识点关系。

## 16. 完成标准

- Vue、Spring Boot、FastAPI 和 MySQL 可以独立启动。
- `schema.sql`、`data.sql` 可在空数据库执行。
- BKT、DKT 可以重复训练或加载现有模型。
- 训练、验证和测试按学生时间顺序切分。
- 保存数据版本、随机种子、参数和真实指标。
- 公开数据实验与合成数据演示明确分开。
- 模型绑定课程 ID 和目录版本。
- 推荐包含真实、可解释原因。
- 事件重复接收不重复更新掌握度。
- 同一学生课程的并发事件不会覆盖已提交的掌握度。
- 快照缺失事件可进入待补偿状态，并可在快照补齐后重试成功。
- 目录版本变化后，旧模型、推荐和活动路径不会继续作为当前结果使用。
- 推荐完成后可以展示掌握度历史、推荐和路径的动态变化。
- FastAPI 异常时可以降级。
- 不虚构实验指标。
- 个人项目不依赖其他成员数据库。

非功能验收目标：

- 普通查询在演示数据规模下 P95 响应时间不超过 500ms。
- BKT 单事件更新 P95 不超过 300ms。
- 推荐生成 P95 不超过 2s。
- FastAPI 调用超过 1～2s 后触发降级。
- 单批最多 500 个事件，支持返回成功、重复和失败明细。
- 所有跨系统响应包含 `traceId`，异常日志可按 `traceId` 定位。
- 服务重启后模型注册、掌握度、推荐、路径和事件消费状态不丢失。

## 18. 风险与应对

| 风险 | 级别 | 应对措施 |
|---|---|---|
| 第一周范围过大 | 高 | 严格执行 P0/P1/P2，先完成 BKT 主闭环，再接入 DKT 和协同过滤 |
| 成员 1 接口或数据延期 | 高 | 第 1 天固定 Mock 响应、事件样例和 UUID；第 7 天替换为真实接口验证 |
| 公开数据模型与演示课程不匹配 | 高 | 公开数据只做实验；演示课程使用课程内合成模型或降级 BKT |
| 重复、乱序或并发事件 | 高 | 唯一约束、批内排序、同学生课程串行化/乐观锁和事务一致性 |
| 目录版本变化 | 中高 | 模型、推荐和路径绑定 `catalogVersion`，变化后立即失效并冷启动 |
| 推荐子分数缺少数据 | 中 | P0 使用四项基线；数据不足时禁用协同过滤并重新归一化 |
| 先修图有环或内容缺失 | 中 | 同步和生成时双重检测；返回明确阻塞原因；准备一门完整验收课程 |
| FastAPI 不可用 | 中 | 短超时；返回已保存结果并按 DKT→BKT→规则基线降级 |
| 模型文件依赖本机路径 | 中 | 使用项目相对路径或容器卷，注册 checksum，禁止提交本机绝对路径 |
| 报告、指标与代码不一致 | 中 | 保存数据哈希、参数、随机种子、映射表和真实实验结果，不手工修改指标 |
