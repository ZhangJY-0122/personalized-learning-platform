# AI 驱动的个性化学习平台统一数据与接口契约

版本：V1.0  
适用服务：教学考试服务、成绩学档服务、个性化服务、Platform BFF、sync-worker

## 1. 契约效力

本文档是三名成员共同遵守的技术合同。第一天确认后冻结 V1.0：

- 删除字段、改变类型、改变枚举含义、改变 URL 均属于破坏性修改，必须升级版本并通知所有成员。
- 新增非必填字段属于兼容性修改。
- 个人项目内部表可以自行扩展，但跨系统字段必须遵守本文档。
- 第二周发现实现差异时，优先在 BFF 或同步适配器中转换，不随意改变契约。

## 2. 数据所有权

| 数据 | 主数据服务 | 其他服务 |
|---|---|---|
| 用户、角色、登录身份 | 教学考试服务 | 只使用 `user_id` 或只读摘要 |
| 课程、章节、知识点、先修关系 | 教学考试服务 | 保存带版本的只读快照 |
| 资源、题目、试卷 | 教学考试服务 | 只读引用 |
| 原始答题、考试提交、即时判分 | 教学考试服务 | 通过事件消费 |
| 正式成绩、排名、学档、错题 | 成绩学档服务 | 通过查询接口读取 |
| 掌握度、推荐、路径、模型 | 个性化服务 | 通过查询接口读取 |

服务不得直接查询或修改其他服务数据库。

## 3. 命名、类型和公共字段

- 数据库字段使用 `snake_case`。
- JSON 字段使用 `camelCase`。
- 跨系统 ID 使用 `CHAR(36)` UUID，API 中作为字符串。
- 时间在数据库中使用 `DATETIME(3)`，API 使用带时区的 ISO 8601。
- 分数范围为 0～100，数据库使用 `DECIMAL(5,2)`。
- 掌握度、概率和权重范围为 0～1。
- 枚举使用英文大写，例如 `STUDENT`、`QUESTION_ANSWERED`。
- 业务表包含 `created_at` 和 `updated_at`。
- 需要删除的业务数据使用 `deleted_at` 软删除。
- 需要并发控制的表增加 `version` 乐观锁字段。
- 所有跨系统响应包含 `traceId`。
- 分页统一使用 `page`、`pageSize`、`total`、`items`。

## 4. ID 与版本规则

1. UUID 由实体所属的主数据服务生成。
2. 其他服务不得根据名称、学号或业务编码重新生成跨系统 ID。
3. `courseCode`、`knowledgeCode`、`questionCode` 只用于展示、搜索和导入，不能替代 UUID。
4. 外部数据集 ID 只存放在 `external_id_map`，不得直接作为线上业务 ID。
5. 课程结构发生变化时更新 `catalogVersion`。
6. 算法模型必须绑定 `courseId + catalogVersion + modelVersion`。
7. 不匹配当前目录版本的模型不得用于在线推理。

## 6. 关键约束与索引

### 6.1 教学考试服务

- `sys_user(username)`
- `course(course_code)`
- `knowledge_point(course_id, knowledge_code)`
- `question(course_id, question_code)`

- `exam_attempt(exam_id, user_id, attempt_no)`

业务约束：

- 先修边禁止自己指向自己。
- 先修关系保存前执行有向环检测。
- 考试提交必须使用幂等键。

## 7. 统一认证

综合模式下，由教学考试服务签发 JWT：

```text
sub = user_id
role = STUDENT | TEACHER | ADMIN
iss = platform
aud = platform-services
jti = token_id
exp = 过期时间
```

规则：

- 请求使用 `Authorization: Bearer <token>`。
- BFF 转发原始 Authorization 头。
- 三个业务服务使用相同环境变量验证签名。
- 服务端校验签名、过期时间、签发方和受众。
- BFF 进行权限初筛，业务服务仍要再次校验权限。
- 学生只能读取自己的成绩、错题、掌握度和推荐。
- 教师只能读取授权课程或班级的数据。
- 成员 2、3 在综合模式下不保存密码并关闭独立用户管理入口。

## 10. 统一学习事件

生产端：教学考试服务。  
消费端：成绩学档服务、个性化服务。  
同步端：综合项目中的 `sync-worker`。

生产接口：

```http
GET /api/v1/integration/events?afterSeq=1200&limit=500
```

消费接口：

```http
POST /api/v1/integration/events/batch
```

事件格式：

```json
{
  "schemaVersion": 1,
  "batchId": "uuid",
  "events": [
    {
      "eventId": "uuid",
      "eventSeq": 1201,
      "eventType": "QUESTION_ANSWERED",
      "userId": "uuid",
      "courseId": "uuid",
      "objectType": "QUESTION",
      "objectId": "uuid",
      "occurredAt": "2026-09-08T20:15:30.123+08:00",
      "durationMs": 45000,
      "attemptNo": 1,
      "correct": false,
      "score": 0,
      "knowledgeItems": [
        {
          "knowledgeId": "uuid",
          "weight": 1.0
        }
      ],
      "sourceService": "teaching-service",
      "traceId": "uuid",
      "attributes": {
        "examId": "uuid",
        "attemptId": "uuid"
      }
    }
  ]
}
```

V1.0 事件类型：

```text
COURSE_ENROLLED
RESOURCE_VIEWED
RESOURCE_COMPLETED
QUESTION_ANSWERED
EXAM_SUBMITTED
RECOMMENDATION_EXPOSED
RECOMMENDATION_CLICKED
RECOMMENDATION_COMPLETED
```

事件规则：

- `eventId` 是全局幂等键。
- `eventSeq` 只由成员 1 生成，用于增量拉取。
- 消费者不得用 `eventSeq` 判断业务唯一性。
- 重复事件返回成功，但不得重复更新统计。
- 每批最多 500 条。
- 部分事件失败时返回失败列表，不要求整批回滚。
- payload 不得包含密码、Token 或密码哈希。
- `occurredAt` 是业务发生时间，`createdAt` 是服务端入库时间。

事件接收响应：

```json
{
  "code": "OK",
  "message": "batch accepted",
  "data": {
    "batchId": "uuid",
    "acceptedEventIds": ["uuid"],
    "duplicateEventIds": ["uuid"],
    "failedEvents": []
  },
  "traceId": "uuid"
}
```

## 11. 同步游标和重试

同步程序每 5 秒拉取一次新事件。每个消费者维护独立游标：

```text
sync_cursor
- cursor_id
- consumer_name
- last_event_seq
- last_success_at
- last_error_at
- last_error_message
- updated_at
```

流程：

1. 读取目标消费者的 `last_event_seq`。
2. 向成员 1 拉取下一批事件。
3. 向目标服务批量投递。
4. 目标返回成功、重复和失败列表。
5. 成功或已确认重复的事件推进游标。
6. 失败事件进入重试记录。
7. 连续失败超过阈值后进入人工检查列表。

## 12. 目录快照和模型版本

成员 1 的 `/courses/{courseId}/structure` 一次返回：

- 课程
- 章节
- 知识点
- 知识点先修边
- `catalogVersion`

成员 2、3 保存只读快照时：

- 不改变原 UUID。
- 不反向修改成员 1 数据。
- 同步成功后记录目录版本和同步时间。
- 遇到未知题目或知识点的事件时先记录待补偿状态，不直接丢弃。

个性化服务加载模型前校验：

```text
model.course_id == request.course_id
model.catalog_version == current.catalog_version
model.status == ACTIVE
```

任一条件不满足时使用 BKT 或规则基线降级。

## 13. 契约验收

三人完成以下检查后，V1.0 才算冻结：

- 所有公共 UUID 字段类型一致。
- 时间、分数、掌握度和枚举格式一致。
- 三个服务能返回统一响应和错误结构。
- JWT 能被三个服务验证。
- 考试提交重复调用不会重复判分。
- 同一事件重复消费不会重复写入。
- 目录版本变化能被成员 2、3 识别。
- 模型目录版本不匹配时不会继续推理。
- OpenAPI 示例与真实接口响应一致。
