## 0. 最终目标

G4 完成后，当前单机电脑网页版应冻结为可独立演示的 M0 核心版：

1. 学生能基于当前可信 BKT 状态生成一条持久化学习路径。
2. 路径严格遵守先修 DAG；每个待学知识点依次包含资源、基础题、进阶题和复测。
3. 题目和资源只有通过服务端校验的 `pathNodeId` 才能推进节点；普通浏览、普通练习和客户端自报不能伪造路径完成。
4. 复测失败后最多自动安排两轮；第二轮仍未达标时进入 `BLOCKED + NEEDS_REVIEW`，不无限生成。
5. 每次重规划保留历史路径；仍有效的完成证据可继承，旧事件不复制、BKT 不重复更新。
6. 目录 JSON 可以作为新版本或历史补偿版本导入；新版本激活后按明确 UUID 映射重建，不按名称猜映射。
7. 管理员可以导入可信事件、查看失败事件、重试和查看重建/导入结果；缺快照事件可在补齐历史目录后恢复。
8. 任一事务、重建、重规划或发布步骤失败，都不留下半条路径、半份掌握度或半激活目录；重启后可继续。
9. G1、G2、G3 的认证、作答、BKT、推荐、反馈及幂等契约全部回归通过。

G4 的完成定义不是“页面能看到路径”，而是本文第 16 节全部关卡通过，并生成真实验收产物。

阶段编号以当前仓库的 `docs/01-scope-and-gates.md` 为准。上级 05 总方案的早期排期曾把“路径”写在 G3 日期栏、把导入恢复写在 G4；实际提交已经将 G3 冻结为推荐与反馈，因此本任务书把尚未实现的路径、版本和恢复统一收口到 G4。这是对实际代码进度的续接，不是删除原 M0 要求。

## 3. 冻结的领域规则

### 3.1 达标、薄弱与待诊断

- `ADEQUATE`：`evidenceCount >= 3 && evidenceWeight >= 2 && mastery >= 0.6`。
- `WEAK`：证据达到上述门槛且 `mastery < 0.6`。
- `INSUFFICIENT`：证据数或权重任一不足；0.2 先验不能称作薄弱。
- 边界 `mastery == 0.6` 视为达标。
- 路径、推荐和掌握度必须调用同一判断函数；禁止各写一份阈值。

### 3.2 `stateRevision` 与路径的关系

`learning_path` 保存两个 revision：

- `origin_state_revision`：生成该路径时的输入版本，永不修改，用于复现。
- `state_revision`：该路径已原子吸收的最新学习状态版本。

规则如下：

1. 普通练习或普通资源行为改变状态时，当前 ACTIVE 路径变为 `INVALIDATED`，并写入一条重规划任务。
2. 带合法 `pathNodeId` 的预期行为不会仅因 revision 增加而让自身路径失效；事务提交时同时把路径的 `state_revision` 更新到新 revision。
3. 路径资源 VIEWED 只把该资源节点从 `PENDING` 变为 `IN_PROGRESS`；不完成节点、不更新 BKT。
4. 路径资源 COMPLETED 完成资源节点，但仍不代表知识点掌握。
5. 路径题事务 A 最多把节点置为 `IN_PROGRESS`；只有对应 `QUESTION_ANSWERED` 在事务 B 成功后才能完成节点。
6. 路径外的新学习证据、目录切换、重建开始都会使旧路径失效；旧路径仍可读取，不能继续提交节点行为。

### 3.3 路径和节点状态机

路径顶层状态只允许：

| 当前状态 | 允许转移 | 触发 |
| --- | --- | --- |
| `ACTIVE` | `COMPLETED` | 所有知识点复测达标 |
| `ACTIVE` | `INVALIDATED` | 非路径状态变化、目录变化、管理员重建或重规划替代 |
| `ACTIVE` | `BLOCKED` | 内容不足、第二轮复测后仍未达标、目录内容运行时失效 |
| `BLOCKED` | 无原地恢复 | 修复内容后生成新 pathVersion，旧路径保留 |
| `INVALIDATED` | 无原地恢复 | 只能生成新版本 |
| `COMPLETED` | 无原地恢复 | 后续新证据如使技能重新薄弱，生成新版本而非改旧记录 |

`NEEDS_REVIEW` 不是顶层状态。第二轮失败时使用：

```text
status = BLOCKED
reasonCode = NEEDS_REVIEW
```

节点状态只允许：

| 当前状态 | 允许转移 | 说明 |
| --- | --- | --- |
| `PENDING` | `IN_PROGRESS` | 已打开资源或已提交题目事务 A |
| `PENDING` | `COMPLETED` | 幂等重放发现可信完成已存在 |
| `PENDING` | `SKIPPED` | 新版本继承有效内容完成，或前置复测已使后续补充节点无须执行 |
| `IN_PROGRESS` | `COMPLETED` | 资源完成事务或题目事件事务 B 成功 |
| `IN_PROGRESS` | `PENDING` | 仅管理员恢复确认事务 A 未产生可消费事件时；正常请求不可回退 |
| 任意终态 | 不可回退 | `COMPLETED/SKIPPED` 不允许再次完成 |

### 3.4 复测轮次

- 自动复测总轮数固定为 2，不是“初始轮次外再加两轮”。
- 初始路径为 `roundNo=1`：资源 → 基础题 → 进阶题 → 复测题。
- 第一轮复测事务 B 成功后，若证据充分且 BKT `>=0.6`，该知识点通过。
- 第一轮复测后仍未达标，重规划生成 `roundNo=2`：一项未使用的补充练习 → 一道未使用的复测题。
- 第二轮复测后仍未达标，路径转为 `BLOCKED/NEEDS_REVIEW`。
- 判断依据是复测事件提交后的 BKT 与证据量，不是仅看该题 `correct`；页面要明确“复测后仍未达到掌握与证据门槛”。
- 每个知识点独立计轮次，禁止使用整个路径的全局重试次数代替。

### 3.5 锁顺序与事务边界

所有会同时碰用户、课程状态、路径或作业的事务统一按以下顺序加锁：

```text
local_user
  -> learner_course_state
  -> learning_path（最新版本）
  -> learning_path_node（sequence_no）
  -> event/replan/import job row
```

禁止反向锁。纯算法计算不得在持锁期间访问网络。目录发布锁课程后，按 `user_id` 升序锁受影响的学习状态。

### 3.6 作业与事件状态机

事件沿用现有状态，不增加 `PROCESSING` 数据库态：

```text
PENDING -> SUCCEEDED
PENDING/FAILED -> FAILED -> PENDING（到期自动重试或管理员重试）
PENDING/FAILED -> PENDING_COMPENSATION -> PENDING（补齐历史快照后）
FAILED -> NEEDS_ATTENTION（第 6 次失败）
```

`PENDING_COMPENSATION` 和 `NEEDS_ATTENTION` 都会阻挡同一用户课程后续事件；不能跳过队首。API 的 `meta.status=PROCESSING/FAILED` 是查询投影，不是新数据库状态。

路径重规划作业：

```text
PENDING -> SUCCEEDED
PENDING/FAILED -> FAILED -> PENDING
FAILED -> NEEDS_ATTENTION（第 6 次失败）
旧 revision 作业 -> SUCCEEDED + resultCode=SUPERSEDED
```

导入作业：

```text
PENDING -> VALIDATING -> SUCCEEDED | SUCCEEDED_WITH_WARNINGS
PENDING -> VALIDATING -> VALIDATION_FAILED
PENDING/VALIDATING -> FAILED -> PENDING（可重试）
FAILED -> NEEDS_ATTENTION（第 6 次失败）
```

`VALIDATING` 是可恢复状态：应用启动时把没有完成时间的 VALIDATING 作业改回 PENDING，并保留 attemptCount。目录发布本身必须单事务；不能出现作业显示成功但目录只发布一半。

重建作业：

```text
PENDING -> REBUILDING -> SUCCEEDED | SUCCEEDED_WITH_WARNINGS
PENDING/REBUILDING -> FAILED -> PENDING
FAILED -> NEEDS_ATTENTION（第 6 次失败）
```

启动时将遗留 REBUILDING 作业和对应 `learner_course_state=REBUILDING` 恢复为 `PENDING + REBUILD_REQUIRED`。旧派生状态始终保留到成功切换。

## 5. 路径算法任务

新增纯 Java 类：

- `server/src/main/java/edu/f21/learningpath/LearningPathPlanner.java`
- `server/src/test/java/edu/f21/learningpath/LearningPathPlannerTest.java`

纯算法不得读取数据库、系统时间、随机数或 Spring Bean。所有输入必须由服务层一次性构造。

### 5.1 输入模型

至少包含：

- `courseId/catalogVersion/plannerVersion/stateRevision`
- 知识点：ID、名称、`sortOrder`、mastery、evidenceCount、evidenceWeight、近 20 次错误率
- 先修边：`source` 是 `target` 的先修
- 当前有效资源：ID、知识点、难度、sortOrder
- 当前有效题目：ID、知识点、难度、sortOrder
- 当前及历史路径中已可信完成的 item、对应知识点、目录和原节点
- 每个知识点已执行的复测轮数及已用题目

所有概率必须有限且在 `[0,1]`；非法数值、环、自环、悬空边、跨课程候选直接拒绝规划。

### 5.2 目标选择

1. 先做稳定拓扑排序：零入度队列按 `sortOrder`，再按 `knowledgeId`。
2. 有 `WEAK` 技能时，沿用 G3 weakness 公式，取前 3 个；平分按拓扑序、再 UUID。
3. 将每个目标的全部“未达标可达前驱”加入闭包；已达标前驱不重复安排。
4. 没有 WEAK 但存在 `INSUFFICIENT` 时，取拓扑序中第一个未达标且其前驱均已达标的点，生成诊断型路径；文案不得称其薄弱。
5. 所有知识点都 ADEQUATE 时，返回 `COMPLETED` 空路径，`reasonCode=null`。
6. 有未达标点但全部被无效图或内容缺口阻断时，返回 `BLOCKED`，列出具体 `knowledgeId + missingRequirements`。

### 5.3 每个知识点的节点选择

首轮要求至少 1 个有效资源和 3 道不同的有效题。题目按 `(difficulty,sortOrder,itemId)` 稳定排序：

1. `RESOURCE`：难度最接近 `clamp(mastery + 0.10, 0.20, 0.70)` 的资源。
2. `BASIC_PRACTICE`：未使用题中难度最低者。
3. `ADVANCED_PRACTICE`：未使用题中难度最高者。
4. `RETEST round 1`：剩余题中难度最接近 `0.60` 者。

第二轮需要再有 2 道未使用题：

1. `REMEDIATION round 2`：剩余题中难度最接近当前 mastery 者。
2. `RETEST round 2`：再从剩余题中取难度最接近 `0.60` 者。

每次取出后从候选集中移除。同一路径全局去重；当前一题一知识点，但算法不能依赖 UUID 前缀或题干文本。内容不足时不得重复同一道复测题凑数，必须 BLOCKED 并报告缺几项。

### 5.4 节点顺序与可操作性

- 知识点按闭包的稳定拓扑序排列。
- 每个知识点内按上面的阶段顺序排列。
- API 为每个节点计算 `actionable`：只有全局第一个非终态节点为 true。
- 已完成且在同课程、当前目录仍存在、类型与知识点仍一致的旧节点可以继承为 `SKIPPED`，写 `carriedFromNodeId` 和原因“已保留可信完成证据”。
- 资源完成只允许跳过同一资源节点，不能据此跳过该知识点题目或复测。
- 题目练习完成只表示该题节点完成；知识点仍必须有复测完成且达标。

## 6. 路径服务、事务与工作器任务

新增：

- `LearningPathController.java`
- `LearningPathService.java`
- `PathReplanWorker.java`，或在现有 `LearningWorker` 中清晰分成 `drainEvents()` 与 `drainPathJobs()`。

### 6.1 显式生成

`POST /students/{userId}/learning-path/generate`：

1. 只允许本人 STUDENT；管理员可读但不能替学生生成。
2. 锁 `local_user`，再创建/锁 `learner_course_state`。
3. 若状态不是 READY，或有非 SUCCEEDED 队首事件，返回 409。
4. 校验幂等记录；请求哈希必须含 `courseId`。
5. 读取同一目录的知识、先修、资源、题目、掌握状态和历史路径。
6. 在内存运行 planner。
7. 提交前重新校验目录版本、目录 hash 和 stateRevision。
8. 将旧 ACTIVE 路径置 `INVALIDATED/STATE_CHANGED`，插入新路径和全部节点，再保存幂等响应，全部同一事务。
9. 同用户课程 `pathVersion = previous max + 1`；依赖用户锁保证并发安全。
10. 同键并发只产生一条路径；不同键并发可顺序生成两个版本，但只有最后一条 ACTIVE，前一条必须保留为 INVALIDATED。

### 6.2 GET 只读

`GET /students/{userId}/learning-path?courseId=...`：

- 不创建 `learner_course_state`、路径、节点或作业。
- 无路径返回：`pathId=null,pathVersion=0,status=null,nodes=[]`，同时 `meta.status=INSUFFICIENT`，reason 为“尚未生成学习路径”，并带 `generated=false`。OpenAPI 中只有 `generated=false` 时允许 status 为 null；不能把未生成伪装成已完成。
- 默认返回最新 pathVersion；历史路径通过新增 `pathVersion` query 参数读取。
- 当前状态处理中时仍返回历史路径，但 `meta.stale=true,status=PROCESSING/REBUILDING/FAILED`。
- `available` 要实时校验当前目录和 canonical ACTIVE 状态；历史节点内容不可用时按钮禁用。
- 读取不增加 revision，不修改 updated_at。

### 6.3 路径归因校验

新增共享方法 `validatePathAttribution(user,course,itemId,catalogVersion,itemType,pathNodeId)`：

- 节点存在；路径属于本人和课程。
- 路径为最新 ACTIVE 版本，目录等于当前目录。
- 节点 `itemType/itemId` 精确匹配请求内容。
- 节点是当前唯一 `actionable` 节点。
- 节点未终结，内容仍 ACTIVE。
- 任一不满足：不存在返回 404，越权返回 403，状态/内容冲突返回 409。

一个请求最多带 `recommendationId` 或 `pathNodeId` 中的一个；两者同时出现返回 400，避免一条行为同时冒充两个来源。

### 6.4 事件消费中的节点推进

将现有事件应用拆成两层：

- `applyLearningState(event,targetCatalog,generation)`：只重算交互、BKT、历史、画像，可在 LIVE 和 REPLAY 调用。
- `applyLiveSideEffects(event,newRevision)`：只在正常实时消费调用，处理推荐可信完成和路径推进。

重建不得调用路径推进。推荐可信完成维持当前唯一键语义，G3 回归必须继续通过。

实时事务 B 的顺序：

1. 锁用户和课程状态，取队首事件。
2. 校验事件 hash、身份、原目录快照和归因。
3. 写学习交互、BKT、历史、画像。
4. 若有合法路径节点，完成该题节点；若是 RETEST，使用更新后的 mastery 判断通过/第二轮/NEEDS_REVIEW。
5. 若没有路径节点且存在 ACTIVE 路径，将旧路径 INVALIDATED，并插入去重后的重规划作业。
6. 更新路径已吸收 revision 或作业触发 revision。
7. 更新 learner state revision、顺序键和 READY。
8. 标记事件 SUCCEEDED。
9. 任何一步失败，以上全部回滚，再由短事务记录事件 FAILED。

### 6.5 资源事务中的节点推进

沿用 G3 `/views` 与 `/completions`：

- 请求体增加可选 `pathNodeId`。
- VIEWED 与 COMPLETED 的幂等 hash 都必须包含它。
- VIEWED：资源行为、revision+1、节点 `PENDING→IN_PROGRESS`、路径 stateRevision 同步，单事务。
- COMPLETED：要求本人曾对同一资源和同一路径节点成功 VIEWED；资源行为、revision+1、节点完成、路径推进同事务。
- 普通资源行为使 ACTIVE 路径 INVALIDATED 并创建重规划作业。
- 两个接口仍不更新 BKT；`updatedMastery=false`。

### 6.6 重规划作业

- 事件工作器先处理学习事件，再处理路径作业，避免用旧 BKT 规划。
- 每个作业在单事务内锁用户/状态、检查 dedupe key 与目标 revision、规划新路径、失效旧 ACTIVE、保存新路径并标 SUCCEEDED。
- 如果已有更新 revision 的作业，旧作业直接 SUCCEEDED 并记录 `SUPERSEDED`，不能反向覆盖新路径。
- 失败回滚后用短事务按 5/15/60/300/900 秒更新；超过 5 次 `NEEDS_ATTENTION`。
- 启动恢复只需要继续扫描 PENDING/到期 FAILED；由于不持久化 RUNNING，不需要猜测租约。
- 管理员重试只把 FAILED/NEEDS_ATTENTION 置回 PENDING，成功作业重试不得新建路径。

## 7. 目录导入、版本激活与补偿任务

### 7.1 目录 JSON 包

目录包字段固定为：

```json
{
  "schemaVersion": 1,
  "publishMode": "ACTIVATE",
  "course": {
    "courseId": "uuid",
    "catalogVersion": "non-reused-string",
    "title": "...",
    "description": "..."
  },
  "chapters": [],
  "knowledgePoints": [],
  "prerequisites": [],
  "resources": [],
  "questions": [],
  "knowledgeMappings": []
}
```

`publishMode`：

- `ACTIVATE`：完整校验后成为课程当前目录。
- `ARCHIVE_ONLY`：补入历史目录供旧事件校验和迁移，不改变 `course.catalog_version`。

限制：请求体最多 10 MiB；目录版本不可复用；所有 UUID 保持输入值；禁止根据名称生成或匹配 ID。

### 7.2 全量校验顺序

1. JSON schema、大小、字段长度、UUID、枚举、难度、选项与答案。
2. 包内 ID 唯一，所有实体 courseId 一致。
3. chapter/knowledge/resource/question 引用无悬空。
4. 先修无自环、跨课程、重复边和环。
5. 每个将进入路径的知识点至少 1 个资源和 5 道有效题，以支持首轮 3 题与第二轮 2 题。
6. 每题答案键存在；单选/判断恰好一个答案，多选无重复。
7. `catalogVersion` 未存在；相同内容 hash 重传返回原作业，不再发布。
8. 映射的 from/to 版本和知识点均存在；一对多或多对一首版拒绝。

任一错误时整个目录不发布，但所有错误写入 `import_error`。禁止“先插一半再报告”。

### 7.3 原子发布

`ACTIVATE` 发布事务：

1. 锁 course。
2. 再检查版本和 content hash 未被使用。
3. 插入完整 snapshot 表和 SAME_UUID/EXPLICIT 映射。
4. 更新 canonical `chapter/knowledge_point/resource/question/prerequisite`；新包中缺失的旧资源/题目置 INACTIVE，不删除历史行。
5. 最后更新 `course.catalog_version`。
6. 将受影响 learner state 置 `REBUILD_REQUIRED`，旧 ACTIVE 路径置 `INVALIDATED/CATALOG_CHANGED`，为每个用户创建 rebuild job。
7. 推荐不删除；其版本/hash 检查会自然显示 stale。
8. 提交后再由工作器逐用户重建；不能在目录事务里调用外部服务。

`ARCHIVE_ONLY` 只插入历史 snapshot 和映射；若有匹配的 PENDING_COMPENSATION 事件，则创建对应重建作业，不改变课程当前版本。

### 7.4 跨版本重建

对每个事件：

1. 先用事件自己的 `catalogVersion` 快照验证 object 和 knowledge，不用当前题目表解释旧事件。
2. 若旧知识点 UUID 在目标目录仍存在，使用 SAME_UUID。
3. 否则只使用 `catalog_knowledge_map` 的 EXPLICIT 映射。
4. 无映射事件保留原始记录，计入 `unmapped_events`，不凭名称猜测、不丢数据库原文。
5. 按 `(occurredAt,COALESCE(sourceEventSeq,eventSeq),eventId)` 重放可映射 QUESTION_ANSWERED。
6. 在内存或事务暂存中得到新 mastery/profile；成功后写入新 modelVersion、切换 learner state catalogVersion、generation+1、revision+1。
7. 旧 modelVersion 掌握记录和历史保留；查询只读当前 state catalogVersion 对应模型。
8. 成功后创建一次路径重规划；失败时事务回滚，旧 mastery 保留，learner state 为 NEEDS_ATTENTION 且查询 stale。

sourceEventId, carriedFromNodeId, reason
```

其中 `reasonCode/sourceEventId/carriedFromNodeId/reason` 可为 null，其余必填；`additionalProperties=false`。

`status` 的 schema 为路径状态枚举加 null；只有 `generated=false` 时允许 null。`generated=true` 时必须是四个路径状态之一。

### 9.2 请求变更

- `PracticeRequest` 新增可选 UUID `pathNodeId`。
- `ResourceActivityRequest` 新增可选 UUID `pathNodeId`。
- 文档写明 `recommendationId` 与 `pathNodeId` 最多一个；实现层显式校验，不能仅依靠 OpenAPI 描述。
- Path GET 增加可选 `pathVersion >= 1`。

### 9.3 状态与错误

- 路径接口标 `x-stage: G4`。
- 路径状态与节点状态使用第 3 节枚举。
- 顶层错误码只用现有 `INVALID_ARGUMENT/UNAUTHORIZED/FORBIDDEN/NOT_FOUND/CONFLICT/INTERNAL_ERROR`。
- 业务原因放 `reasonCode` 或 import error 项，不新增无法统一处理的 HTTP 顶层码。
- 每个正常、空、处理中、BLOCKED、历史 stale、越权、冲突响应均提供真实 schema example。

```

### 10.5 管理员恢复页

## 13. 单元测试关卡

16. 禁止提交 `.env`、Token、数据库密码、原始私人数据或本机绝对依赖路径。

## 19. Luna 执行时的停线条件

遇到以下任一情况，停止新增功能，先修复并在提交说明中记录原因：

- G1/G2/G3 任一回归失败。
- V5 升级丢行、修改旧 snapshot 或 Flyway checksum 改变。
- 路径 GET 产生写入。
- 同一事件导致两次 BKT 或两次节点完成。
- 第一轮失败直接 NEEDS_REVIEW，或出现第三轮。
- 目录发布失败后 `course.catalog_version` 已变化。
- 重建失败后旧 mastery 无法读取。
- stale/INVALIDATED 路径仍能提交节点行为。
- 测试必须依赖主开发库、外网或手工改结果才能通过。
