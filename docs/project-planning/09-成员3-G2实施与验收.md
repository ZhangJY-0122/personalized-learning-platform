# 成员3 · G2 作答与学习状态实施记录

## 1. 交付范围

2026-09-10，G2本地学习闭环验收通过。本阶段按电脑网页版交付，不开发手机App，也不以手机布局作为验收条件。G2打通了：

登录学生 → 打开题目 → 提交选项 → 服务端判分并保存 → 本地事件消费 → 更新规则/BKT、画像及历史 → 网页查询结果。

推荐、反馈、资源完成事件、学习路径、完整目录/事件批量导入和正式模型实验不在本次已完成清单中。教师仍可浏览授权课程；个人学习结果只允许本人和管理员访问，教师课程统计后续实现。

本次不向主库批量填入模拟学习记录。验收产生的作答、故障触发器和回放数据均在独立测试卷中；验收截图中的数值来自测试实际执行，不代表主库学生已有这些记录。

## 3. 关键行为

### 提交与幂等

- 只接受当前学生身份，questionId、answer、catalogVersion；不允许客户端指定correct、userId、时间或来源。
- 单选可提交选项键或单元素数组，多选按数组处理；校验选项存在、题型、重复选项和长度。
- Idempotency-Key是UUID，按用户+作答操作绑定归一化请求哈希。并发同键只保存一次；同键异内容409。
- POST重放返回首次结果，包括原submissionId/eventId和首次PENDING状态；GET读取实时消费状态。
- 网页保留当前标签页的未确认请求。网络响应丢失、刷新后重新打开同一题，仍用原键重试；“再练一次”明确新增一条记录。
- sessionStorage会随标签页关闭清除；已保存的作答不受影响，重新登录可查历史。跨标签页未确认请求恢复尚未实现。

### 两个事务与恢复

事务A锁用户和用户课程状态，保存判分与PENDING事件，一起提交或回滚。事件时间由服务端生成，eventSeq由本地表生成。客户端不能伪造可信事件。

事务B先锁用户课程，再按(occurredAt,eventSeq,eventId)处理队首，同时提交交互、BKT、历史、画像、revision和SUCCEEDED。失败全部回滚，再用短事务记录失败。失败或待修复的队首不允许后续事件越过。

自动重试延迟为5、15、60、300、900秒；首次失败后最多自动重试5次，仍失败为NEEDS_ATTENTION。缺快照转PENDING_COMPENSATION；管理员修复引用后可重试。该缺快照分支属于保护逻辑，本次故障注入主要覆盖SQL写入失败，不宣称完成完整目录补偿系统验收。

晚到事件将课程标为REBUILD_REQUIRED，不错误追加到末尾。管理员可按已保存的同目录可信事件排序重建：成功原子替换派生结果并递增generation/revision；失败保留旧结果，查询标stale。进程重启后未完成事件继续处理，中断的REBUILDING转为待重建状态。

### 数值与展示

- BKT固定演示参数L0=0.2、T=0.1、G=0.2、S=0.1；有限性检查，结果截断至[1e-6,1-1e-6]。
- 当前本地题是一题一知识点、权重1；不是多技能生产映射的最终实现。
- 证据数量>=3且权重>=2才允许按0.6阈值判薄弱。初始20%是先验，网页明确标“证据不足”。
- Java规则基线使用最近最多20次有效交互，score=(1+Σw×correct)/(2+Σw)，无证据为0.5。掌握度接口分别返回ruleScore/ruleEvidenceCount，当前页面主展示BKT，不把规则得分称作潜在掌握度。
- 画像只统计已成功处理的交互。未采集学习用时和资源偏好，返回null，不填假数据。
- 请求期间查询使用一致事务快照；处理中或失败时stale=true，网页提示旧结果不能当作最新结果。

## 4. 接口与代码位置

请求/响应细节以f21-personalized-learning/docs/openapi.json为准，版本0.3.0。G2实现：

- POST /practice/submissions，GET /practice/submissions/{submissionId}
- GET /students/{userId}/practice-history?courseId=...，分页1起、默认20、最大100
- GET /students/{userId}/mastery?courseId=...
- GET /students/{userId}/profile?courseId=...
- POST /admin/events/{eventId}/retry
- POST /admin/students/{userId}/rebuild?courseId=...

代码入口：server/src/main/java/edu/f21/practice/，规则/BKT在edu/f21下；前端交互状态与幂等重试在web/src/practice.js，页面在web/src/main.js。

管理员接口需要管理员Bearer令牌。它们目前是维护API，尚未制作完整导入/作业管理页面。普通用户只能刷新状态，不能通过再次提交假装修复原事件。

## 6. 剩余风险与下一关卡

1. 只适用于本地单实例开发演示；生产密码管理、HTTPS、登录限流、安全审计、备份恢复及依赖漏洞检查仍未完成。G1记录的Flyway/MySQL版本警告仍需关注。
2. 目录只完成G2所需的题目/知识点快照，不等于完整版本化导入。跨版本映射、目录发布、资源/先修快照和完整补偿作业需后续完善，当前不开放静默切换。
3. 同版本重建采用锁定整课的事务，限制最多10000条；尚未做万条规模和并发性能验收，不承诺30秒重建目标已达成。扩大数据前优化重建画像聚合、查询索引及任务调度公平性。
4. 反复练同一道题会产生新的有效证据并影响BKT，这符合当前事件规则，但不能解释为真实教学效果提升。正式实验需独立题库/数据切分。
5. 题库内容仍是开发样例。后期填充时先校验答案、知识点关联、难度与复测分组，再扩充模拟学生和行为，不直接修改历史快照。
6. 下一阶段G3：推荐批次与状态版本绑定、候选过滤、真实子分数和解释、反馈幂等。GET只读，过期结果标stale；不把点击或阅读直接变成BKT掌握证据。

## 7. 2026-09-10 复审补充

发现1项G2口径遗漏：画像activityDays原先统计全部历史活跃日期，05方案要求近7日。已改为UTC当天及前6个自然日（0～7），排除未来日期；GET实时按窗口统计，避免没有新作答时保留过期天数。student_profile.activity_days仅是事件处理时的派生缓存，不能直接当作实时窗口值；查询接口以实际交互窗口为准。总作答数、正确率口径不变，不删除旧历史。

补充验证：当天和第6天计入、第7天前和未来日期排除、同天去重、全部记录过期时返回0而总作答数保留、只读查询不增加revision。全部测试修改都在隔离测试库，并恢复测试交互时间后再做网页验收。
