1. 不修改、重命名或重新格式化 V1～V6。

4. 每个场景使用独立命名卷、独立 server/web 端口，不依赖 18083/15173。
5. 场景间不得共享业务状态；PATH-10 需要自行从空卷重建第一轮前置状态。
6. 业务前置数据只允许来自迁移、登录 API、练习 API、资源 API、目录导入或事件导入。
7. 不允许 SQL 插入、更新或删除 mastery、path、submission、event、catalog、job 等业务行。
8. SQL 只允许：读取 schema/行数/hash/状态、创建和删除隔离故障触发器。
9. 故障触发器必须记录名称，并在 `finally` 中删除；即使删除失败也必须执行 `docker compose down`。
10. `docker compose down` 不加 `-v`，保留场景卷供审查。
11. 不复用或停止 `f21-preflight`、毕业论文项目及其他用户容器。
12. 不把 Token、JWT secret、数据库密码、SQL、堆栈或本机敏感路径写入产物。
13. 任一场景失败时，顶层 `passed=false`，进程非零退出；不得继续 G4C-09。
14. 不通过降低鉴权、幂等、事务、BKT、路径顺序或映射约束让测试通过。
15. 不新增 G5 的数据、模型、训练或实验代码。

## 3. Runner 先行重构要求

开始补场景前，先让 runner 支持真正的场景级隔离，避免后一个场景依赖前一个场景的状态。

### 3.1 建议结构

在 `tests/g4_acceptance_live.py` 中抽取：

```text
ScenarioStack
├── project = f21-g4-<scenario>-<8hex>
├── serverPort = 动态空闲端口
├── webPort = 动态空闲端口
├── volume = <project>_f21-data
├── jwtSecret = 每个栈随机值，仅内存保存
├── up(targetVersion=None, worker=False)
├── waitHealth()
├── api(...)
├── sqlReadOnly(...)
├── sqlFaultOnly(...)
├── restartServer(worker=None)
├── imageIds()
└── close() -> compose down，不带 -v
```

每个 `scenario()` 自己进入和退出 `ScenarioStack`。组合动作可以在一个场景内连续完成，但不同场景不共享数据库。

### 3.2 端口与卷

- 不继续硬编码所有场景共用 18098/15188。
- 先由操作系统分配空闲端口，再传给 Compose。
- 项目名必须包含场景短名和随机后缀。
- 产物保存每个场景的 `composeProject`、`volumeName`、端口、镜像摘要。
- 最终 `volumesRetained` 应是数组，而不是单一布尔值。

### 3.3 HTTP 断言

每次请求至少验证：

- HTTP status。
- 响应 `code`。
- 响应 JSON schema。
- body `traceId` 与 `X-Trace-Id` 一致。
- 不含 password、token、secret、stack trace 或 SQL。
- 幂等场景比较业务 ID、revision、行数和 payload hash。

### 3.4 等待策略

不得使用固定长 sleep 判断 worker 完成。统一实现有限轮询：

- 健康检查最多 120 秒。
- 单事件处理最多 40 秒。
- 路径重规划最多 40 秒。
- 重建最多 60 秒。
- 每次轮询 300～500 ms。
- 超时错误必须包含最后一次非敏感状态与相关 job/event ID。

### 3.5 产物写入

运行期间写入临时结果；只有所有场景完成后再原子替换 `artifacts/g4-acceptance.json`。任何异常仍要写出失败场景和已完成场景，但不能把旧的成功产物误保留为本次结果。

建议提交：

```text

```

   - 推荐、反馈、资源活动数量。
   - 关键表按主键排序后的内容 hash。
6. 使用当前 server 镜像连接同一卷并迁移至 V7。

- V1～V5 checksum 与升级前完全一致。

- 新增 G4 表为空或只有契约允许的初始化行。

- `reason_code=NEEDS_REVIEW`。

## 7. 批次 R4：G4-MAP-01～03 跨版本映射

三个场景分别使用独立项目和独立卷。所有旧事件通过练习 API 创建；新目录通过 catalog import 创建。

### 7.1 独立 Python BKT 基准

在测试侧实现纯 Python 回放，参数与冻结契约一致，但不得调用生产 Java 方法。输入按以下稳定顺序排列：

```text
occurred_at
source_event_seq（存在时）
event_seq
event_id
```

基准输出至少包含：

- knowledgeId。
- mastery。
- evidenceCount。
- evidenceWeight。
- 每一步 before/after。
- replayGeneration。

比较浮点值时使用冻结容差，不得通过放大容差掩盖算法差异。

### 7.2 G4-MAP-01：SAME_UUID

- 新旧目录保留相同 knowledgeId。
- 两侧快照均存在。
- ACTIVATE 后验证自动建立唯一 SAME_UUID 映射。
- 执行管理员 rebuild。
- 新版本 mastery/evidence 与独立 Python 回放完全一致。
- replay 不增加 event/submission/resource_activity，不推进路径或推荐。

### 7.3 G4-MAP-02：EXPLICIT

- 新版本使用新的 knowledgeId。
- 目录包显式提供旧 ID→新 ID 的 EXPLICIT 映射。
- 验证不会按名称、标题、题干或数组位置猜测。
- 重建后证据只落在目标 knowledgeId。
- 旧 mastery/history 保留，新状态原子切换至新 catalogVersion。
- 重复导入/重建不产生重复映射或重复历史。

### 7.4 G4-MAP-03：无映射

- 新版本移除或替换旧 knowledgeId，且不提供映射。
- 重建必须返回 SUCCEEDED_WITH_WARNINGS。
- processed/mapped/unmapped 数量可对账。
- 原事件、submission 和旧快照保留。
- 不把事件映射到同名知识点。
- 管理员 job 查询可看到 unmappedEvents 和 warning/error 信息。
- learner state 不应在不完整重建时伪装成完全成功。
