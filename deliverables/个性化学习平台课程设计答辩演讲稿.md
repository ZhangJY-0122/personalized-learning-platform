# 《基于知识追踪与混合推荐算法的个性化学习平台》答辩演讲稿

建议时长：8—10 分钟。答辩时不必逐字朗读，可根据老师现场反应适当删减。

## 第 1 页：封面

各位老师好，我是张佳仪。我的课程设计题目是《基于知识追踪与混合推荐算法的个性化学习平台》。下面我将从项目背景、系统设计、核心算法、功能实现和测试结果五个方面进行汇报。

## 第 2 页：项目背景与设计目标

传统在线学习平台通常能够记录学生看过哪些内容、做过哪些题，但很难进一步回答三个问题：学生到底掌握了什么，系统为什么给出这个推荐，以及下一步应该学习什么。

本项目针对三个断点展开设计。第一，浏览、完成和答题行为容易混在一起，学习证据不够清楚。第二，如果状态更新由前端临时拼接，就容易出现重复提交、状态覆盖和不可追溯。第三，推荐只给结果，不解释原因，学习路径也没有显式处理先修关系。

因此，本项目的目标是把一次作答转化为可审计的学习事件，再由掌握度估计、混合推荐和学习路径规划，给出下一步学习任务。

## 第 3 页：核心业务闭环

这一页把系统功能串成一条业务闭环：先完成登录和课程授权，再发生资源浏览或作答；作答经过服务端判分后进入可信事件队列；事件工作器更新掌握度和历史；推荐与路径模块读取版本化状态，给出下一步学习任务。

这里最关键的边界是，只有服务端确认的有效作答才能更新 BKT。资源浏览、反馈和重复请求会进入可追溯台账，但不会被直接当成掌握证据。

## 第 4 页：系统范围与总体思路

系统包括学生端和管理员恢复台两部分。

学生端完成本地账号、课程授权、课程资源、客观题练习、服务端判分、历史记录、掌握度、推荐和学习路径。管理员恢复台支持事件查询、目录导入、失败重试、事件补偿和状态重建。

整个系统围绕四个约束展开：服务端拥有业务单一写入权；同一个操作具备幂等性；推荐、路径和学习状态都携带版本信息；出现故障后可以重试和恢复。

右侧数据流展示了核心闭环：学生作答后，服务端完成校验和判分，生成待消费事件；事件工作器再更新交互、画像、BKT、历史和状态版本，最后由推荐和路径模块读取这些状态。

## 第 5 页：系统总体架构

系统采用前后端分离架构。前端使用 Vue 3、Vite、Pinia 和 Axios，主要负责页面、导航、输入和状态展示。后端使用 Java 17 和 Spring Boot 3，负责认证、授权、课程读取、服务端判分、事件消费、BKT、推荐、路径以及管理员恢复接口。数据库使用 MySQL 8，数据库结构由 Flyway 管理，系统通过 Docker Compose 在本地独立部署。

这一页最重要的是职责边界。前端不能直接修改掌握度，资源浏览不能直接更新 BKT，推荐和路径必须绑定目录版本与状态版本，页面也不能把暂存状态当成最终状态。这样才能保证页面展示的结果与服务端真实状态一致。

## 第 6 页：数据库概念结构与 E-R 模型

数据库概念结构分为总体关系和模块关系两层。

从总体关系看，用户通过课程授权访问课程快照，课程快照包含知识点、资源和题目。学生提交作答后形成作答记录和可信学习事件，事件更新掌握状态，并作为推荐批次和学习路径的依据。

从模块关系看，课程与授权模块负责课程版本和访问范围，学习状态模块负责作答、事件、画像和掌握度，推荐与路径模块负责推荐项目、反馈、路径节点和资源行为。

关键实体都保存版本或来源字段，例如 catalogVersion、stateRevision 和 sourceEventId。这样当课程目录或算法策略变化时，系统仍然可以解释某一次推荐或路径是依据什么生成的。

## 第 7 页：从作答到掌握度的可信状态链

这一页说明系统如何保证学习状态可信。

事务 A 负责校验课程版本、用户权限、幂等键和请求哈希。校验通过后，服务端完成判分，并保存一个 PENDING 状态的学习事件。

事务 B 由事件工作器负责。工作器按 occurredAt、eventSeq 和 eventId 的顺序消费事件，写入学习交互、学生画像、BKT 掌握度、状态历史和 stateRevision。如果事务 B 失败，业务写入会回滚，事件保留重试信息；失败次数达到阈值后进入 NEEDS_ATTENTION，由管理员处理。

这样，同一个幂等键重复请求时只返回首次业务结果；同一个幂等键提交不同内容时会返回冲突；系统重启后也可以根据事件状态继续恢复。

## 第 8 页：核心算法

系统包含掌握度、推荐和学习路径三个算法模块。

首先是 BKT 掌握度。系统只使用服务端确认的 QUESTION_ANSWERED 事件更新知识点掌握度，资源浏览、资源完成和反馈不会直接改变 BKT。演示参数为 L0 等于 0.2、T 等于 0.1、G 等于 0.2、S 等于 0.1。固定样例中，三次错误后掌握度下降到约 0.1145，后续六次正确后恢复到约 0.9996。这个结果用于验证实现与参考向量一致，不代表真实学生的学习效果。

其次是混合推荐。推荐综合薄弱匹配、难度匹配、内容匹配和偏好分量。缺失分量会从总权重中剔除后重新归一化，推荐项目会保存分数、分量、关联知识点和解释原因。

最后是 DAG 学习路径。系统按照知识点先修关系组织资源、基础题、进阶题和复测节点。复测失败最多进入第二轮，外部学习行为或目录迁移会触发路径重规划。

## 第 9 页：学习端功能展示

左侧是学习资源页面，学生可以查看课程资源并记录浏览和完成行为。这里需要强调，资源行为进入行为台账，但不会直接更新 BKT。

右侧是掌握度页面，系统展示知识点掌握状态、证据量和学习历史。页面状态覆盖正常、空数据、处理中、失败和过期等情况，处理中状态来自后端事件状态，而不是前端临时假设。

学生端的主要流程是：登录、选择课程、阅读资源或完成练习、等待事件处理，再查看历史、掌握度、推荐和路径。

## 第 10 页：推荐与路径展示

推荐页面会展示推荐内容以及薄弱匹配、难度匹配、内容匹配和偏好等解释原因，避免只给出一个无法理解的推荐分数。

学习路径页面按照先修关系排列学习任务，包含资源、练习和复测节点。推荐批次和学习路径都绑定 stateRevision、目录版本和策略版本。当学习状态发生变化时，旧推荐可以被标记为过期，旧路径也可以被重新规划。

## 第 11 页：管理恢复与测试验收

管理员恢复台提供事件列表、状态筛选、目录 JSON 导入、事件导入、重试和重建功能。目录导入先完成全量校验，再执行原子发布；跨目录只使用 SAME_UUID 或显式 UUID 映射，不按名称、标题或数组顺序猜测。

最终验收结果如下：G1 通过 66 项接口检查；G2 通过 109 项 HTTP 检查；G3 通过 139 项 HTTP 检查；G4 的核心场景通过 38 项，HTTP 检查 59 项，数据库断言 33 项。Chrome 浏览器验收中，页面错误、控制台错误、网络错误和未处理异常均为空。

这些结果说明系统不仅能够完成页面展示，也覆盖了权限、幂等、事务回滚、事件重试、目录迁移、推荐过期、路径重规划和管理员恢复等关键场景。

## 第 12 页：项目总结

最后总结一下，本项目完成了从作答到掌握度的可信状态链，实现了可解释混合推荐和 DAG 学习路径，并通过版本、幂等、重试和重建保证系统可追溯、可复核、可恢复。

这次课程设计让我认识到，个性化学习系统的难点不只是把页面和算法连接起来，更重要的是定义清楚学习证据、状态边界和故障恢复方式。只有先保证数据链路可信，推荐和路径结果才有实际意义。

我的汇报到这里。感谢各位老师，欢迎提问。

## 可能的答辩问题与回答要点

### 1. 为什么资源浏览不能直接更新 BKT？

因为浏览只能说明学生接触过内容，不能证明已经掌握。项目把资源浏览和资源完成记录为行为台账，把服务端确认的作答结果作为 BKT 的主要证据，从而避免把“看过”误判为“学会”。

### 2. 为什么要把判分和事件消费拆成两个事务？

这样可以把请求响应和异步学习状态更新分开。判分成功后先保存 PENDING 事件，事件工作器再更新掌握度和历史。如果状态更新失败，可以保留事件并重试，不会因为一次异常丢失学习证据。

### 3. 推荐算法是不是机器学习模型？

当前版本的在线推荐采用可解释的混合排序规则，综合薄弱、难度、内容和偏好四类分量。项目另外保留了离线 DKT 烟测管线，但没有把合成数据训练结果包装成真实教学效果。这样更适合课程设计阶段的可解释和可验收要求。

### 4. 目录版本变化后，旧推荐和旧路径怎么办？

推荐批次和路径都会绑定目录版本与状态版本。目录迁移使用稳定 UUID 或显式映射，旧结果不会静默覆盖新版本；如果旧结果不再适用，系统会将其标记为过期或触发重规划。

### 5. 当前系统距离生产环境还有哪些差距？

当前系统定位是本地独立部署的课程设计成果，已经覆盖核心功能、数据一致性和恢复验收，但还没有宣称达到公网生产安全等级。后续可以继续增强多租户、细粒度审计、真实教学数据评估、模型监控和高并发部署能力。
